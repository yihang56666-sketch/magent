# magent：Codex 原生子智能体编排 Skill 面试与演示指南

更新：2026-09-07。本指南只描述仓库已有实现；行为验收与测试结论以审查记录为准。

## 1. 先把项目说对

项目仓库叫 magent，交付物是 codex-native-subagent-orchestrator 这个 **Codex Skill**，不是多智能体运行时、SaaS 或模型训练项目。它把“什么时候委派、给谁、允许读什么、交付什么证据、失败如何收尾”写成可加载的操作协议。

最核心的一句话：**原生工具负责创建和运行子智能体；Skill 负责约束任务划分与证据交接；主智能体负责最终判断和修改。**

适合展示的岗位：AI 应用工程、开发工具、测试工程、工程效率。若应聘底层模型训练或分布式运行时岗位，应主动承认本项目不覆盖这些领域。

### 30 秒介绍

> 我整理了一个面向 Codex 原生子智能体的编排 Skill。重点不是增加代理数量，而是判断哪些问题值得并行，并给每个只读角色一个有范围、证据格式和停止条件的任务。主智能体独占写入和最终验证。仓库包含入口协议、角色目录、分派模板、示例、28 项结构契约测试和手动验收案例。它依赖宿主工具，不冒充独立运行时或权限沙箱。

### 3 分钟介绍顺序

1. **问题**：普通“多找几个 AI 看看”容易重复调查、等待依赖、结论互相矛盾；共享工作区还会发生不可归因的修改。
2. **取舍**：不再做一层 Python/HTTP 执行框架；直接使用宿主原生工具，减少生命周期和账号配置的重复实现。
3. **设计**：分派准则 → 一个任务包 → 原生 agent ID → 有限证据回传 → 主模型核验 → 显式关闭。
4. **可靠性修复**：把“等待超时”与“子智能体停止”分开；把 dirty status 改成差异和内容指纹；明确立即阻塞的工作留在主模型。
5. **证据**：展示真实协议与一个失败回归；现场运行结构测试。真实协作轨迹与静态测试分开解释。
6. **限制**：只读靠指令和事后审计，真正权限由宿主提供；没有证明每次委派都会更快或更准确。

运行链路：用户任务与授权 → 本地分析下一步 → 委派判断 → 根据实际工具 schema 分派 → 保存 agent ID → 本地主线继续 → 收集证据 → 比对工作区基线 → 主模型编辑/验证 → 关闭不用的 agent。

这里没有自建调度器、消息队列、数据库或模型 SDK。文档角色是提示词标签，不是可以随意塞进原生 API 的 agent_type 参数。

## 3. 为什么这样设计

### 3.1 不是所有难题都值得委派

判断不是“任务复杂就多开代理”。只有子问题足够独立、上下文可以有界传递，且主模型同时有有用工作可做时，委派才有价值。

反例：一个两行配置错误，下一步必须知道某个字段含义，主模型自己查一次即可。委派后原地等待只增加调用和通信成本。

正例：主模型实现输入校验时，一个只读 Reviewer 检查既有权限边界；两者问题独立，核验结果能在集成前发现风险。

### 3.2 主模型唯一写入

共享目录下两个 agent 都修改同一函数，会产生冲突、覆盖和归因困难。这个 Skill 故意牺牲部分并行修改速度，以换取清楚的写入责任。不要把其他项目里采用的“互不重叠写范围工人”说成此 Skill 的默认协议。

### 3.3 人数越多不等于证据越强

默认 1–3 个，第四个仅在安全敏感或明确跨域且独立时考虑。一个 critique 只分给一个合适专家；不要让两个专家重复同一份泛化审查，再把重复当成独立支持。

### 3.4 内容基线比 Git status 更强

文件已经是 M 状态时，子智能体再次修改它，git status 仍然只显示 M。只比较文件名看不见内容变化。协议要求 scoped 未暂存/已暂存二进制 diff，以及允许范围内的文件指纹，包含已有 untracked 文件。记录时排除秘密、依赖和缓存；这仍不是防篡改审计系统。

### 3.5 超时不是终止

wait 的空结果只说明这个观察窗口没有拿到终态；不能由此重开同一任务。保存原 ID，发一次有界补证请求或继续核对原 handle。只有确认原任务终止/关闭后，才评估一个更窄的替代任务。

close_agent 返回的是关闭请求前状态，不能伪装成新的“已关闭实测状态”。完成的 agent 也可能继续占并发槽，应收集后显式关闭。

## 4. 现场 5 分钟演示

### 无原生工具也能稳妥演示的部分

从仓库根运行：

~~~powershell
python -X utf8 -B -m unittest discover -s tests -v
~~~

预期为当前 28 项通过。解释其中结构断言的能力边界，再打开 dispatch-contract.md 展示怎样把“检查项目”缩成一个可核验问题。不要在不支持原生工具的环境里靠手动复制提示词伪造“agent 已运行”。

### 支持原生子智能体时的有界演示

1. 用一份无敏感信息的小仓库；明确授权一个只读 Reviewer。
2. 主模型先保存指定文件的 status、diff 和 SHA-256；不扫描整个用户目录。
3. 将任务限定为一个源文件与一个测试文件：“这项空值处理是否与测试一致？”
4. 在原生工具 UI 中展示真实返回 ID；不从文档里凭空复制不存在的参数。
5. 主模型并行核对 README 的运行命令，不等待委派来决定自己的第一步。
6. 收集包含路径、具体触发输入和不确定性的返回包；主模型复核一个关键结论。
7. 比较文件指纹，证明该次演示范围内未出现意外写入；显式关闭该 ID。
8. 用一句话结束：“这证明此样例的完整交接走通，不证明所有任务均会遵守指令。”

验收情景见 references/acceptance-cases.md。一次执行只能证明相应情景，不足以填满所有案例或得出成功率。

## 5. 本轮可讲的具体改进

| 旧问题 | 风险 | 修改和可展示证据 |
| --- | --- | --- |
| 深度任务自动触发被误当授权 | 在用户没要求时产生额外子任务/成本 | 把授权门放在 Workflow 首步，并有结构回归 |
| 把主模型下一步的阻塞工作直接委派 | 主模型闲等，协调开销大于收益 | 增加 immediate blocker 留本地规则 |
| dirty 文件只看 status | 看不出同一路径二次修改 | diff + scoped fingerprints 契约 |
| 等待超时就开替代任务 | 重复任务并发，旧任务仍在运行 | pending/terminal/close 分离，优先原 ID |
| 一个 critique 示例给两个专家 | 重复调查与人数规则矛盾 | 模式、rubric、示例人数一致化 |
| 测试只检查关键词存在 | 相互矛盾的条款仍可能通过 | 增加位置/结构/映射检查，并公开承认剩余语义盲区 |

新增 7 项结构回归在修复前表现为 6 项失败、1 项缺失文件错误，修复后总计 27 项通过；2026-09-07 又新增 1 项契约文件隐私自指防护，总计 28 项通过。不要把这个数字说成 28 次真实 agent 成功运行。

## 6. 技术追问与回答要点

**Q：这不就是一份提示词吗，工程价值在哪里？**

是声明式协议，不应该夸成运行时。价值在显式输入/输出契约、任务边界、失败语义、跨文件一致性、版本化回归和验收方法。是否降低成本/提高质量仍需同类任务的对照评估。

**Q：为什么不用 LangGraph / AutoGen？**

本项目的部署对象已经是提供原生 subagent 的 Codex 会话。再增加调度框架会引入第二套生命周期和配置，但未必解决当前问题。如果需求变成长期持久任务、跨机器队列、统一配额，才值得重新选择运行时。

**Q：你怎样保证代理只读？**

不能单靠 Skill 保证。协议明确禁止写，限制允许范围，并在返回后核对内容。强保证需要宿主只读工具权限、隔离文件系统或不可变挂载；这里不虚构权限沙箱。

**Q：代理给出错误结论怎么办？**

报告是待核验建议。要求源文件位置、复现步骤、已执行/仅建议命令和不确定性；主模型复核影响决策的点。证据不足时只给原 agent 一次窄问题补证，而不是投票或无限加人。

**Q：主模型和专家意见相反怎么办？**

对比同一输入、同一版本和控制流，实际跑最小复现；若差异来自假设，记录假设而不是“多数通过”。无法证明则保留风险，不强行修复。

**Q：怎样衡量收益？**

未来可固定任务集、工具版本、模型与权限，比较单代理/有界委派的总耗时、全部模型 token、有效缺陷、误报和回归率。当前没有这组对照数据，所以不能承诺提速百分比或节约费用。

**Q：结构测试能检测什么？**

缺字段、角色/人数不一致、关键安全与生命周期条款被删除、示例不合规。不能证明模型理解条款，也不能证明原生工具行为和文档长期一致。需要真实交互轨迹与负面验收。

**Q：没有 spawn_agent 怎么办？**

直接声明当前环境不能原生分派，主模型继续本地工作。不会构造虚假的 agent 日志、prompt 文件或模拟 worker 来冒充原生执行。

**Q：如何控制权限和费用？**

明确授权、最小团队、独立问题、软证据预算、停止条件。软预算不是运行时硬限额；第三方发布、账户、付费工作和凭据操作都不能委派给只读角色。

**Q：哪些是你的工作，哪些来自 AI/宿主？**

区分协议整理、取舍、用例和验收，与 Codex 的模型、工具执行和 UI。若实现中使用 AI，诚实说是 AI 辅助；重点讲自己能复核的失败路径，不把宿主已有能力描述成自行开发。

## 7. 简历表述和禁止夸大的说法

可用表述：

> 设计并维护 Codex 原生子智能体编排 Skill，约束只读角色、分派包、dirty workspace 基线和超时/关闭生命周期；通过标准库 unittest 维护 28 项结构契约，并设计原生行为验收案例。

不要说：自研多智能体执行引擎；实现分布式调度；保证子代理无法写文件；提速数倍；28 个端到端场景全部通过；支持所有模型平台。

## 8. 面试前核对单

- 能不用读稿解释为何不委派立即阻塞的工作。
- 能说明工具 ID、pending、completed、close request 的区别。
- 能现场运行结构测试并解释一个断言不够强的例子。
- 能对照真实工具 schema 写一个合法分派包。
- 能说明 baseline dirty 与 agent 新写入如何区分。
- 演示环境没有原生工具时，明确改演静态协议，不伪造执行。
- 不打开个人 token、私有项目内容或未授权目录。
