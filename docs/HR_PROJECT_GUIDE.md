# magent：Codex 原生子智能体编排 Skill 面试与演示指南

更新：2026-09-30。交付物是 **可加载的 Codex Skill**，不是多智能体运行时、SaaS 或模型训练项目。

## 一句话定位（开场 10 秒必须说对）

**原生工具负责创建和运行子智能体；magent 负责约束任务划分与证据交接；主智能体负责最终判断和修改。**

适合岗位：AI 应用工程、开发工具、测试工程、工程效率。  
若面试官期待「自研 Agent 框架/调度器」，主动承认本项目不做执行层。

## 30 秒介绍

> 我整理了面向 Codex 原生子智能体的编排 Skill。重点不是增加代理数量，而是判断哪些问题值得并行，并给每个只读角色一个有范围、证据格式和停止条件的任务。主智能体独占写入和最终验证。仓库有入口协议、角色目录、分派模板、示例、33 项结构契约测试和验收案例。

## 五个失败模式 → 五条可测试不变量

| 失败模式 | 不变量 |
|---|---|
| 一难就多开代理 | 授权门：复杂度 ≠ 授权；加载 Skill ≠ 分派许可 |
| 主 Agent 空等 | 立即阻塞的工作 keep-local |
| 共享工作区二次修改不可见 | 内容指纹基线，不只看 `git status` |
| wait 超时被当成失败 | pending ≠ terminal；保留原 agent ID |
| 完成仍占并发槽 | 显式 close/archive；close 返回的是前状态 |

## 最难追问

**这不就是提示词吗？**  
声明式协议。价值在：输入输出契约、失败语义、跨文件一致性、版本化回归。不是「再写一长段 system prompt」。

**为什么不 LangGraph/CrewAI？**  
宿主已是提供原生 subagent 的 Codex 会话。再加框架 = 第二套生命周期。通用框架做执行引擎；magent 做其上的判断、边界与核验。

**怎么保证只读？**  
指令 + 事后工作区审计。**不能**单靠 Skill 强保证；强保证需宿主只读权限/隔离 FS。不虚构沙箱。

**33 项测试证明什么？**  
证明协议结构完整、关键短语与字段在位。**不证明**模型一定遵循指令、**不证明**端到端成功率。

**有性能数据吗？**  
无对照评估。不承诺「提速数倍」。分派本身有成本，默认 1–3 个。

**和 v1 运行时什么关系？**  
v1 自建 3k 行 Python 执行状态机，后来证明真正有价值的是分派契约与核验规则；v2 收敛为纯 Skill，v1 归档保留演进记录。

**我的部分 vs AI 的部分？**  
协议整理、失败模式产品化、用例与验收设计、边界诚实度；模型执行来自宿主。
